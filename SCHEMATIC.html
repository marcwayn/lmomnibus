Premise

One catalog, many instruments

Every tool on this site is a different lens over the same normalized model catalog. That constraint is the product strategy: once ingest is right, each new tool is a view, not a project.

The reference point is the familiar per-token cost calculator: type in token counts, read a table of every model. It works, but it hands you a 400-row wall and asks you to find yourself in it. LMOmnibus inverts that — you name what you're looking for first, by vendor, by name, or by when it shipped, and the tool answers only about the handful of models you actually care about.

Below the surface, the harder difference is that most calculators model pricing as two numbers per model. Real pricing is not two numbers. It is tiered by prompt length, discounted by batch mode, surcharged by fast mode, split between cache reads and cache writes, and — for some vendors right now — temporarily promotional. Getting those right is the reason to build this rather than use what exists.

Architecture

Where the data goes

The load-bearing decision: search crosses the network, arithmetic does not.

Why this shape

A 415-model catalog is only ~25 KB gzipped, so shipping all of it to the browser is tempting. Don't: search quality is where this product competes, and fuzzy ranking, facet counts, and vendor aliasing all want to live server-side where they can change without a redeploy of the WASM bundle. Ship the ranking from the server and the arithmetic to the client — each where it belongs.

Deliberately absent

  • No database. The catalog is a file. Snapshots are files in git. A database buys nothing until there are user accounts, and it costs an operational surface from day one. Revisit at Tool 05, not before.
  • No JavaScript framework and no Tailwind. Hand-authored CSS against the token set in § Design. The visual identity is the differentiator; a utility framework's defaults pull straight back toward the look this site is defined against.
  • No client-side Tailwind-style runtime, no CDN anything. Fonts self-hosted in public/fonts, subset to Latin.

Domain

The model, in types

crates/lmo-core/src/model.rs 
use jiff::civil::Date;
use rust_decimal::Decimal;
use std::collections::BTreeMap;

/// USD per 1,000,000 tokens. Never f64 — money is Decimal, everywhere.
pub type UsdPerMTok = Decimal;

pub struct Model {
    pub key: ModelKey,              // "anthropic/claude-opus-5"
    pub display_name: String,       // "Claude Opus 5"
    pub vendor: Vendor,
    pub released: Date,             // <- the third search axis
    pub retires_on: Option<Date>,   // drives the Tool 05 countdown
    pub knowledge_cutoff: Option<Date>,
    pub context_tokens: u32,
    pub max_output_tokens: Option<u32>,
    pub modalities: Modalities,
    pub capabilities: Capabilities, // tools, structured output, reasoning efforts
    pub scores: Option<Scores>,     // intelligence / coding / agentic
    /// Standard is always present. Batch, Fast, Priority are optional
    /// *modes of this model* — never separate catalog entries.
    pub rates: BTreeMap<RateMode, RateCard>,
    pub provenance: Provenance,
}

pub enum RateMode { Standard, Batch, Fast, Priority }

pub struct RateCard {
    pub input:          UsdPerMTok,
    pub output:         UsdPerMTok,
    pub cache_read:     Option<UsdPerMTok>,
    pub cache_write_5m: Option<UsdPerMTok>,
    pub cache_write_1h: Option<UsdPerMTok>,
    pub reasoning:      Option<UsdPerMTok>, // billed apart by some vendors
    pub image_input:    Option<Decimal>,    // USD per image
    pub web_search:     Option<Decimal>,    // USD per call
    /// Long-context tiers, ascending. Empty means a flat rate.
    pub tiers:          Vec<RateTier>,
    /// Time-boxed promo that supersedes the above while live.
    pub promo:          Option<Promo>,
}

pub struct RateTier {
    pub above_input_tokens: u32,
    pub input:  UsdPerMTok,
    pub output: UsdPerMTok,
    pub cache_read: Option<UsdPerMTok>,
}

pub enum Provenance {
    /// Transcribed from the vendor's own pricing page. Wins on conflict.
    FirstParty { checked: Date },
    /// Derived from the aggregate feed. Broad coverage, weaker authority.
    Aggregate  { fetched: Date },
}

The tier rule, which is easy to get wrong

Vendors price the whole request at whichever tier its prompt lands in. It is not marginal like a tax bracket — crossing 272K tokens does not price the first 272K at the low rate. Encode that once, in one place:

crates/lmo-core/src/cost.rs 
impl RateCard {
    /// Whole-request tiering: the highest threshold the prompt clears
    /// prices every token in the request, input and output alike.
    pub fn tier_for(&self, prompt_tokens: u32) -> Rates<'_> {
        self.tiers
            .iter()
            .rev()
            .find(|t| prompt_tokens > t.above_input_tokens)
            .map(Rates::Tier)
            .unwrap_or(Rates::Base(self))
    }
}
Property test worth writing on day one

For every model with tiers, cost must be monotonic in prompt length: adding one token can never lower the bill. That single property catches inverted comparisons, off-by-one thresholds, and tier lists that were never sorted.

Catalog

Ingest, and the override layer

Broad coverage from the aggregate feed; authority from files you maintain by hand.

The aggregate feed gives 415 models across 42 vendors with release timestamps, context lengths, modality flags, cache pricing, and capability benchmarks — every field the eight tools in § Roadmap need, from a single unauthenticated endpoint. What it does not give is authority. It reports what a reseller currently charges, which is not always what the vendor lists.

So ingest runs a merge, and curated files win on conflict. This is where the Sonnet 5 case gets handled:

data/providers/anthropic.toml 
[[model]]
key      = "anthropic/claude-sonnet-5"
released = "2026-06-10"

# List price. The aggregate feed currently reports 2.00/10.00, which is
# the introductory rate — correct today, wrong for any annual budget.
[model.rates.standard]
input          = 3.00
output         = 15.00
cache_read     = 0.30
cache_write_5m = 3.75

[model.rates.standard.promo]
input  = 2.00
output = 10.00
until  = "2026-08-31"

[model.rates.batch]
input  = 1.50
output = 7.50

The calculator then shows the promotional rate as the default with the list rate one toggle away, and annualized projections quietly use the list rate. That behaviour is the whole point of the override layer, and it is not something an aggregator can do for you.

Normalization steps, in order

  1. Collapse mode suffixes. :batch and -fast variants fold into their parent's rates map instead of becoming rivals in the result list.
  2. Resolve aliases. Pointer entries (alias_target) collapse onto their target so "latest"-style handles do not appear twice.
  3. Convert units. Feed prices are USD per token as strings. Parse to Decimal, multiply by 1e6, store as UsdPerMTok. Parse, never f64::from_str.
  4. Derive release month. The created timestamp becomes a civil date; the canonical slug's date suffix (…-20260723) corrects it where they disagree.
  5. Apply overrides. Curated files replace matching fields and stamp Provenance::FirstParty.
  6. Validate, then swap. Reject the whole batch if any model has zero rate modes or an unsorted tier list. A bad refresh must never replace a good catalog.
Failure posture

The upstream feed is a third-party dependency on your critical path. Ingest never touches the live catalog until validation passes, and the server boots from the newest snapshot on disk. If the feed is down for a week, the site serves last-known-good prices with a visible "as of" date rather than an error.

Search

Three axes, one field

Provider, name, and release window — combinable, and none of them mandatory.

crates/lmo-core/src/query.rs 
pub struct Query {
    /// Fuzzy across display_name + key + vendor. "op5", "sonnet",
    /// "gpt 5.6 sol" all resolve.
    pub text: String,
    /// OR within the facet, AND against the others.
    pub vendors: Vec<Vendor>,
    /// Inclusive, month granularity: (2026, 1)..=(2026, 8)
    pub released: Option<MonthRange>,
    pub min_context: Option<u32>,
    pub modes: Vec<RateMode>,
    pub limit: usize,               // default 25
}

/// Fuzzy score is the spine; recency is a gentle multiplier so a 2024
/// model never outranks its 2026 successor on an equally good match.
/// Capped at 1.35x — recency must not override an exact name match.
pub fn rank(fuzzy: u16, age_months: u32) -> f32 {
    let recency = 1.0 + 0.35 * (-(age_months as f32) / 18.0).exp();
    fuzzy as f32 * recency
}

"If I switch from this model to that one, what breaks?" Side-by-side of modalities, tool-calling and structured-output support, reasoning effort levels, tokenizer family, knowledge cutoff, and caching — with differences highlighted and matching rows collapsed by default.

Feeds on: modalities · capabilities · knowledge_cutoff

05

Price Ledger

"What changed?" Diffs the snapshot archive: price cuts and rises with dates, models added, and a retirement countdown for anything with a published end-of-life. The one tool that gets better purely by the site having existed longer.

Feeds on: data/snapshots/*.json · retires_on

06

Switch Planner

"I spend $4,200/month on Opus 5. Rank my alternatives by what I'd save and what I'd give up." Composes 01, 02, and 04: savings on the left, capability delta and breaking spec changes on the right, so the tradeoff is one row per candidate.

Feeds on: Tools 01 + 02 + 04

07

Cache Break-even

"At what cache hit rate does prompt caching start paying for itself?" Cache writes cost more than base input — Opus 5 writes at $6.25 against a $5.00 base — so there is a real hit rate below which caching loses money. Solve for it and plot it.

Feeds on: cache_read · cache_write_5m · cache_write_1h (246 models)

08

Tokenizer Bench

"How many tokens is my actual prompt?" The same text tokenizes differently per family, and a 35% swing between families moves the whole cost comparison. Counts across families, then hands the result straight to Tool 01 instead of making you guess an input size.

Feeds on: architecture.tokenizer · local tokenizer crates compiled to WASM

The omnibus argument

Tools 02 through 08 need no ingest work that Tool 01 has not already paid for. That is what makes a suite viable for one person to maintain — and it is worth resisting any tool proposal that would break the pattern by demanding its own data pipeline.

Design

Instrument, not dashboard

The identity comes from where the subject actually lives: commodity price boards, metering, spec sheets. Tokens are sold by the million, like a utility — so the site is built to look like something that measures, not something that predicts.

The neutrals are biased, not grey. Ground and ink both carry a faint green cast pulled from the accent. A pure neutral reads as unconsidered; a neutral tuned toward the accent reads as chosen, and it makes the pine accent sit in the page rather than on top of it.

The accent is semantically loaded. On a price board green means down and red means up. Making the brand colour also mean "cheaper" means the primary action, the active filter, and the best-value card are all the same colour — one bold hue doing three jobs, and every other element staying quiet.

Geometry and motion

  • 3px radius, maximum. Never pills, never rounded-2xl. Instruments have edges.
  • Elevation is a hairline, not a shadow. One border and a surface shift. No blur, no glow, no glass.
  • The meter rule — a tick-marked divider — separates major sections. It is the one ornament, and it is a measuring scale.
  • 8px baseline grid. Dense tables, generous section gaps.
  • Everything left-aligned. Centred columns are for marketing pages, not spec sheets.
  • Numbers get the emphasis: large mono figure, small muted unit suffix. The unit is never the same size as the value.
  • Motion is 140ms and functional — hover feedback, a figure tweening when a number changes. Nothing reveals on scroll.
  • Light theme is the default. Dark is fully designed, not inverted.

Sequence

Build order

Ordered by dependency, not by appeal. Each milestone has an exit condition you can actually check.

M1
lmo-core, headless. Types, cost engine, tier logic, search scoring. No web, no server, no HTML. Exit: cargo test green, including the monotonic-cost property test, and cargo check --target wasm32-unknown-unknown passes.
M2
Ingest. Fetch, normalize the four cases from § Premise, merge overrides, write a snapshot. Exit: a committed snapshot where the four normalizations are individually asserted in tests — batch folded, alias resolved, tier parsed, Sonnet 5 promo split from list.
M3
Design system. tokens.css and main.css, both themes, on a static page that exercises every component before any of them is dynamic. Exit: light and dark both legible in all three theme states, including OS-dark with no explicit choice stamped.
M4
Server + search. Axum, ArcSwap catalog, boot-from-snapshot, the two server functions, the refresh task. Exit: "op5" returns Claude Opus 5 first; a failed refresh leaves the old catalog serving and logs loudly.
M5
Tool 01. Search island, bench island, workload inputs, URL codec, all six interaction states. Exit: a shared URL renders correct figures with JavaScript disabled.
M6
Model pages + open catalog. 415 SSR spec sheets and the public /catalog.json. Exit: sitemap generated from the catalog at build time; every page is reachable and cached.
M7
Tool 02. Price–Capability Frontier — the first proof that a second tool costs a view, not a project. Exit: shipped with no changes to lmo-catalog. If that constraint breaks, the architecture claim was wrong and it is cheap to find out here.
Open

Decisions still yours

QuestionRecommendationWhy it matters now
How much of the catalog do you curate by hand? Start with the five vendors people actually budget against; let the aggregate feed cover the long tail with a visible "aggregate" provenance badge. Curation is the ongoing maintenance cost of this site. Five vendors is roughly an hour a month; forty is a job.
Hosting shape? A single small VM or container. The catalog lives in RAM and the app is one binary — this does not want serverless, where cold starts would reload the catalog per invocation. Decides M4's boot sequence and whether snapshots ship inside the image.
Do model pages get editorial notes? Yes, eventually — a paragraph of human judgement per major model is the thing an aggregator structurally cannot copy. Changes whether M6 pages are generated or authored, which is hard to reverse later.
Is lmomnibus.dev the domain? Check availability before the wordmark hardens. Cheap now, annoying after the design system is built around it.
